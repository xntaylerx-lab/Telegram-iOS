# Visual Quote — журнал решений

Каждое решение: что выбрано, почему, что было альтернативой. Новые записи добавляются снизу.

## M0 — Окружение (2026-10-12)

### D-001. Клон живёт в `~/Developer/Telegram-iOS`, ветка `visual-quote`
Причина: в пути `~/Documents/Telegram contest` есть пробел, Documents может синхронизироваться с iCloud. Так задано в задании (раздел 4).

### D-002. Сборка для симулятора через `Make.py build` с фиктивной подписью из `build-system/fake-codesigning`
Выбрано из двух допустимых путей задания (`generateProject --disableProvisioningProfiles` или `build` с fake-codesigning).
Причина: `build` даёт готовый `bazel-bin/Telegram/Telegram.ipa`, на который завязан штатный workflow обновления приложения в симуляторе из `CLAUDE.md` репозитория (копия `.app` из `.ipa`). Для `generateProject` нужен Xcode-проект и сборка через xcodebuild, а путь Xcode-managed signing требует настоящий Apple team.
Команда (из корня клона):
```
python3 build-system/Make/Make.py --cacheDir="$HOME/telegram-bazel-cache" build \
  --configurationPath="$HOME/Developer/telegram-config/build-config.json" \
  --codesigningInformationPath=build-system/fake-codesigning \
  --buildNumber=1 --configuration=debug_sim_arm64
```

### D-003. Конфиг сборки — копия в `~/Developer/telegram-config/build-config.json` с `team_id = C67CF9S4VU` и `bundle_id = ph.telegra.Telegraph`
Причина: `Make.py` отбирает provisioning-профили по точному префиксу `team_id.bundle_id` в `application-identifier` профиля (`BuildConfiguration.py`, `copy_profiles_from_directory`). Профили в `fake-codesigning` выписаны только на `C67CF9S4VU.ph.telegra.Telegraph`; при другом `bundle_id`/`team_id` ни один профиль не подходит, `aps-environment` не находится и сборка завершается с ошибкой до запуска Bazel.
Оригинальный `config/build-config.json` в папке проекта не изменён; изменённая копия лежит вне репозитория и вне git. Ключи api_id/api_hash в репозиторий не попадают: `build-input/*` в `.gitignore`.
Статус: ждёт подтверждения Ники (bundle id совпадает с официальным Telegram; для симулятора это безопасно, для распространения — нет).

### D-004. Для Xcode 26 нужен отдельный компонент Metal Toolchain
Факт: первая сборка упала на `MetalCompile` с ошибкой `cannot execute tool 'metal' due to missing Metal Toolchain`. Компонент скачан командой `xcodebuild -downloadComponent MetalToolchain` (688 МБ). Это обязательный шаг при настройке окружения с нуля — записать в README.

### D-005. Тестовое окружение Telegram (test DC)
Факт из кода: клиент поддерживает test DC только через аргумент запуска `--ui-test` (`AppDelegate.swift`, `isUITest`). В этом режиме используется отдельная папка данных `telegram-ui-tests-data`, которая **стирается при каждом запуске**, и регистрация идёт на тестовые серверы. Тестовые номера `99966XYYYY` (страна `+999`), код подтверждения — цифра DC пять раз (`docs/ui-testing.md`).
Проверено на симуляторе: при запуске с `--ui-test` клиент подключается к тестовым DC (149.154.167.40, 149.154.175.10, 149.154.175.117), без флага — к продакшн-адресам. Отдельного переключателя в Debug Settings нет. Следствие: без небольшой правки кода тестовый аккаунт не переживает перезапуск приложения. Решение, как вести разработку (реальные аккаунты или test DC с правкой), — за Никой после M0.

### D-006. Разработка ведётся на тестовых серверах Telegram (test DC), не на реальных аккаунтах
Решение Ники (2026-10-12). Причины: не нужен реальный номер и нет риска ограничения аккаунта, зарегистрированного через неофициальную сборку; фейковых персонажей для демо можно завести как отдельные тестовые аккаунты с именами и аватарками.
Как запускать: оба симулятора — с аргументом `--ui-test` (отправитель через XcodeBuildMCP `launch_app_sim` с `launchArgs`, получатель через `xcrun simctl launch <udid> ph.telegra.Telegraph --ui-test`).
Открытый вопрос на M1: нужна ли маленькая правка, чтобы тестовый логин не стирался при каждом запуске (`AppDelegate.swift` удаляет `telegram-ui-tests-data` при старте с `--ui-test`).
Реальные аккаунты понадобятся не раньше M3, для проверки вида сообщения в обычном Telegram.

### Заметка к D-006 (2026-10-12, вечер). Тестовые серверы отвергают фиксированный код
Факт: с нашим api_id `auth.sendCode` на test DC проходит (сервер отвечает `sentCodeTypeSms(length: 5)`, миграция между DC1–DC3 работает), но `auth.signIn` с кодом `XXXXX` возвращает `400: PHONE_CODE_INVALID` на всех трёх DC. Проверено через экран входа и через headless-путь репозитория (`--ui-test --delete-test-account <номер>`, без push-токена) — результат одинаковый. Собственный UI-тест репозитория (`Telegram/Tests/Sources/UITests.swift`) использует тот же сценарий с api_id команды Telegram. Единственная оставшаяся переменная — наш api_id. Логи приложения содержат api_hash открытым текстом: не пересылать их никому.
Статус: открыто. Варианты: проверить «Test configuration» для приложения на my.telegram.org/apps; попробовать повторную отправку кода звонком; откатиться на реальные аккаунты (риск описан в D-006).

### D-007. Переход на реальные аккаунты (отменяет D-006)
Решение Ники (2026-10-12, вечер). Причина: тестовые серверы отвергают фиксированный код с нашим api_id (см. заметку к D-006), повлиять из кода нельзя. Оба симулятора запускаются без `--ui-test`: отправитель через XcodeBuildMCP `launch_app_sim` без аргументов, получатель через `xcrun simctl launch <udid> ph.telegra.Telegraph`. Данные теперь в обычной папке `telegram-data` и переживают перезапуск. Риск ограничения свежего аккаунта принят осознанно.

## M2 — Выделение у отправителя (2026-10-12, вечер)

### D-008. Выделение строится на `ImageObjectSeparation`, подсветка — свой оверлей в новом модуле `VisualQuote`
Причина: в клиенте уже есть вырезание объекта для стикеров (Vision на устройстве, CoreML-модель `u2netp` в симуляторе), новый код его только вызывает. Обводка из `StickerCutoutOutlineView` не переиспользована: она с частицами и завязана на экран редактора; вместо неё подсветка считается из маски фильтрами CoreImage (два варианта: свечение и обводка). Точки встраивания: хук `contentLongTapAction` в `ZoomableContentGalleryItemNode` (3 строки) и секция в `ChatImageGalleryItemNode`. Флаг `visualQuote` в Debug Settings, в нашей сборке включён по умолчанию.

### D-009. Два подводных камня симулятора, оба обойдены внутри `VisualQuote`
1. CoreML-путь `ImageObjectSeparation` масштабирует маску обратно по `image.size` в поинтах; картинка галереи имеет `scale = 3`, поэтому маска получалась втрое меньше и смещалась. Решение: детектор передаёт копию изображения со `scale = 1`. На устройстве (путь Vision) проблемы нет; в upstream-код не лезем.
2. Маска после `CISharpenLuminance` в живом графе CoreImage выходит за 0…1, из-за чего инверсия и умножение давали яркую полосу по контуру и «пелену» по всему кадру. Решение: `CIColorClamp` на входе и перерисовка результата в премультиплицированный CGContext перед отдачей в слой.
Следствие для демо: в симуляторе модель выделяет один «главный» объект на фото (на снимке с тыквами — всю группу оранжевых), при касании вне него срабатывает кольцо. Поэлементное выделение — только на iPhone.

### D-010. Интерактивные проверки в симуляторе
В XcodeBuildMCP этой сессии нет инструментов нажатий. Для тапов и удержаний используется встроенный в Claude Code инструмент iOS Simulator (не `cliclick`/`osascript`/`screencapture`). Скриншоты экранов с личной перепиской в отчёты не попадают.

### Открыто после M2 (выбор Ники)
- Вариант подсветки: A «свечение» или B «обводка» (скриншоты `screenshots/m2/01`, `02`).
- Место кнопки «Reply»: сейчас стеклянная кнопка под выделением; альтернатива — в нижней стеклянной панели галереи.

### D-011. Выделение — редактируемая рамка, а не контур объекта (решение Ники, 2026-10-13)
Вместо свечения/обводки по маске показывается рамка с уголками, как в кадрировании фото в редакторе Telegram (размеры уголков и зон захвата взяты из `TGPhotoCropAreaView`): остальное фото затемняется, уголки тянутся, рамка двигается целиком, пока она активна — зум и прокрутка фото выключены. Vision только предлагает рамку по умолчанию вокруг найденного объекта; если объекта нет, рамка ставится вокруг точки касания.
Причины: это прямой родственник текстовой цитаты (выделение правится ручками); по сети уходит только прямоугольник, значит отправитель и получатель видят одно и то же; польза не зависит от качества распознавания и одинакова в симуляторе и на устройстве. Код свечения/обводки удалён из модуля (остался в истории git, коммит a0a6f55f85).

## M3 — Отправка (2026-10-13)

### D-012. Транспорт координат — вариант B (невидимая ссылка); вариант A отвергнут сервером
Проверено одной отправкой: клиент положил область в `poll_option` ответа, сервер принял сообщение, но вернул `messageReplyHeader` с `pollOption: nil` — поле молча отброшено для сообщения без опроса. Поэтому работает вариант B: к тексту ответа добавляется символ нулевой ширины U+200B с сущностью `textUrl`, URL вида `https://example.com/visual-quote#<base64url>` несёт закодированную область (формат `VQ1` + тип + 6×Float32), превью ссылок отключается флагом `no_webpage`. Сервер вернул сущность без изменений. Домен example.com зарезервирован для документации и никуда не ведёт.
Локально область по-прежнему живёт в `innerSubject = .pollOption(bytes)` (композер, панель ответа): это готовый канал от галереи до панели без правок TelegramCore; перед отправкой `ChatControllerNode.sendCurrentMessage` вынимает её оттуда, обнуляет `innerSubject` и прикрепляет к первому текстовому фрагменту. В обычном Telegram такое сообщение выглядит как обычный ответ на фото (проверено на нашем же клиенте: пузырь не отличается от соседних).
В продакшене вместо этого — поле ответа рядом с `todo_item_id` / `poll_option`.

### D-013. Панель ответа показывает фрагмент 36×36 перед заголовком
В активном компоненте панели (`ChatInputMessageAccessoryPanel`) миниатюра была закомментирована upstream; для Visual Quote добавлен `VisualQuoteCropView` (кроп из лучшего локального представления фото, декод не больше 1024 px), заголовок остаётся «Reply to <имя>», подзаголовок «Photo». Нативный заголовок «Reply to Poll Option» для нашего `pollOption` подавлен.

## M4 — Получатель (2026-10-13)

### D-014. Заголовок ответа показывает фрагмент из оригинала, размер — множитель высоты строки
Фрагмент режется из лучшего локального представления фото (сначала миниатюра, после загрузки — полное; сигнал `visualQuoteCropImage` в модуле VisualQuote), рисуется тем же `TransformImageNode`, что и обычная миниатюра ответа, со скруглением 4, как у неё. Размер задаётся константой `VisualQuoteLayout.replyImageScale` (обычная миниатюра — 2 высоты строки): вариант 1 — 3, вариант 2 — 4.5 (скриншоты `screenshots/m4/01` и `04`). Высота заголовка растёт под фрагмент. Если исходное сообщение недоступно (удалено или не загружено в контекст), заголовок рисуется как обычный ответ без фрагмента — код upstream не меняется.

### D-015. Нажатие на заголовок открывает галерею на оригинале с приближением к области
Передача через новый случай `GalleryMediaSubject.visualQuoteRegion(Data)` (модуль AccountContext, все существующие `switch` по этому enum имеют `default`). Для цитаты галерея открывается в режиме одиночного сообщения (`standaloneMessage`), потому что для истории чата (`peerMessagesAtId`) субъект до элемента не доходит; листание к соседним фото в этом режиме недоступно — приемлемо для перехода по цитате. После завершения перехода из пузыря (0.45 с) фото приближается к области с запасом 35% вокруг, в пределах максимального зума галереи, и на 1.4 с показывается та же рамка, что у отправителя (без интерактива). Проверено записью экрана (`screenshots/m4/07`).

### D-016. Переход по цитате: затемнение вокруг области без рамки, и оно не исчезает (решение Ники, 2026-10-13)
Вместо короткой вспышки рамки с уголками (1,4 с, как в D-015) галерея затемняет всё фото вокруг цитируемой области и оставляет так до закрытия. Рамки, уголков и обводки нет: у `VisualQuoteFrameNode` появился режим `.highlight` (только слой затемнения, без жестов), а сам слой лежит внутри зумируемого контента, поэтому следует за зумом и прокруткой. Это один и тот же путь для получателя и для отправителя, когда тот нажимает на свою отправленную цитату. При выборе области у отправителя рамка с уголками остаётся: она нужна, чтобы тянуть границы. Новое удержание в галерее снимает пассивное затемнение и показывает редактируемую рамку.
Причина: читающему нужно только увидеть, о чём речь; рамка выглядит как приглашение редактировать.

### Заметка к D-016 (2026-10-13). Контраст подсветки у получателя
Ника: затемнения 0,4 без обводки мало. Два варианта (сравнение `screenshots/m4/14`): A — затемнение 0,65 без обводки (`12`); B — затемнение 0,45, как у кадрирования в редакторе Telegram (`TGPhotoCropView`), плюс обводка 1 pt белым 0,7 по скруглённому контуру без уголков (`13`). В B толщина обводки пересчитывается под текущий зум (`scrollViewDidZoom`), чтобы на экране всегда был 1 pt. Выбор за Никой; в коде сейчас B.
Размер фрагмента: Ника выбрала самый крупный, 8 высот строки (вариант 4).

### D-017. При переходе по цитате область центрируется на экране (решение Ники, 2026-10-13, отменено D-028)
Раньше `zoom(to:)` упирался в край фото, и область у края оставалась выше центра. Теперь зум и смещение считаются вручную, а недостающее место у края добавляется как `contentInset` скролла; отступ снимается с анимацией, как только пользователь начинает перетаскивать или зумить (`scrollViewWillBeginDragging` / `scrollViewWillBeginZooming`). Скриншот `screenshots/m4/15`.


### D-018. Проверки данных у получателя и сброс миниатюры (2026-10-13)
В рамках продолжения M4 декодер отвергает неизвестный тип, некорректные координаты и
область за пределами фото. Для Float32 допускается погрешность 0,000001 у края,
после чего область ограничивается границами изображения. При превращении визуального
ответа в обычный на то же фото восстанавливается обычная миниатюра: раньше неизменившаяся
ссылка на медиа могла оставить старый кроп.
Полная сборка debug_sim_arm64 и 4081 проверка кодека прошли. Сценарии UI и догрузка
ещё не подтверждены интерактивно; см. m4-verification.md. Размер 8x и вариант B сохранены,
новых UX-решений не принято, M4 не закрыт.


### D-019. Вариант B утверждён Никой (2026-10-13)
Ника выбрала вариант B для просмотра цитаты: затемнение вокруг области 0,45 и тонкая белая обводка 1 pt с прозрачностью 0,7, без уголков. Подсветка сохраняется при просмотре и следует за зумом и перемещением фото. Это закрывает выбор контраста из заметки к D-016; код и установленные сборки уже используют этот вариант. Интерактивные проверки M4 остаются открытыми; утверждение вида не означает их прохождения.


### D-020. Контекст цитаты сохраняется при недоступном оригинале (2026-10-13, отменено D-022)
После теста удаления Ника отметила, что исчезновение всего блока цитаты делает ответ
непонятным, и согласилась продолжить с компактной плашкой. Визуальный ответ сохраняет
полосу и фон цитаты с локализованными строками «Фото» / «Сообщение не существует».
Картинка не сохраняется отдельно. Формулировка охватывает недоступный оригинал,
поскольку клиент не всегда знает причину отсутствия. Проверено после перезапуска
в светлой и тёмной теме; нажатие показывает стандартное пояснение.


### D-021. Зум с активным выделением (уточнение Ники, 2026-10-13)
Ника попросила уменьшать масштаб фото, сохраняя активную область. Это меняет
ограничение D-011: одним пальцем правится рамка, двумя масштабируется и перемещается
фото. Рамка хранит координаты относительно оригинала и следует за изменением вида.
После закрытия рамки восстанавливается обычное управление одним пальцем.
Проверено в симуляторе 2026-10-13: пинч в обе стороны и перемещение двумя пальцами двигают фото, рамка остаётся на тех же клетках, один палец двигает рамку, Reply даёт тот же фрагмент (`screenshots/m4/20`–`25`).


### D-022. Удалённый оригинал: заголовок исчезает, как везде в Telegram (решение Ники, 2026-10-13, отменяет D-020)
Плашка «Photo / Message doesn't exist» убрана. Если исходное сообщение недоступно, визуальный ответ ведёт себя как любой ответ на удалённое сообщение: заголовок не рисуется, пузырь остаётся обычным текстом. Причина: та же логика, что и везде в приложении, и плашка мигала бы, пока история догружается. Активация через VoiceOver в этом случае ничего не делает (как у обычного сообщения без ссылки).


### D-023. Маркер транспорта стоит в начале текста, а не в конце (2026-10-13)
Причина подчёркивания всего текста у визуального ответа в тёмной теме: Telegram подчёркивает ссылки, когда цвет ссылки совпадает с цветом текста (`stringWithAppliedEntities`, `underlineAllLinks`), а CoreText выбрасывает хвостовой U+200B из глифов строки и для его индекса `CTLineGetOffsetForStringIndex` возвращает 0. `InteractiveTextComponent` строит прямоугольник подчёркивания от этой нулевой позиции до конца строки. Проверено отдельной программой на macOS: для маркера в начале обе позиции равны 0, подчёркивание нулевой ширины. Поэтому `VisualQuoteTransport.attach` теперь ставит маркер первым символом и сдвигает остальные сущности на его длину; старые сообщения с маркером в конце по-прежнему читаются. Фильтр отрисовки `visibleEntities` в нашем клиенте остаётся как вторая защита. Подтверждено Никой в обычном Telegram на телефоне в тёмной теме: текст чистый.
Побочный эффект редактирования (проверено): область переживает правку текста, но редактор (`refreshTextUrls`) растягивает ссылку на соседнее слово, и после сохранения это слово выглядит ссылкой. Решение, нужно ли вычищать маркер при редактировании в нашем клиенте, за Никой.


### D-024. Редактирование визуального ответа: маркер вырезается из редактора и возвращается при сохранении (2026-10-13)
Ника получила после редактирования обычный ответ без фрагмента. Композер Telegram не рассчитан на ссылку на невидимом символе: `refreshTextUrls` растягивает её на соседнее слово, а любая правка в начале текста или замена текста целиком стирает маркер вместе с областью. Поэтому в нашем клиенте при входе в режим Edit маркер и его сущность убираются из текста (`VisualQuoteTransport.detach`, обе точки входа в редактирование в `ChatControllerLoadDisplayNode`), а при сохранении область берётся заново из исходного сообщения и прикрепляется к новому тексту тем же `attach`, что и при отправке; превью ссылки отключается. Работает и для старых сообщений с маркером в конце. В обычном Telegram редактирование такого сообщения по-прежнему может сдвинуть или потерять область: это ограничение транспорта, записано в README.


### D-025. Область терялась, если исходное фото не было в загруженной истории чата (2026-10-13)
Ника получила ответ без фрагмента после выделения на фото из альбома. Причина не в альбоме: при возврате из галереи чат ищет исходное сообщение. Отдельно проверено, что фото из альбома, открытые из самого чата, работали и раньше.


### D-026. Заголовок визуальной цитаты устроен как заголовок текстовой цитаты (решение Ники, 2026-10-13)

### D-034. Область покидает reply subject в одном месте для всех путей отправки (ревью, 2026-10-13)
Ревью диффа ветки нашло, что маркер области добавлялся только в `sendCurrentMessage` для текстовых фрагментов, а остальные ~30 путей отправки (стикер, фото с подписью, голосовое, кубик, inline-результат бота) передавали `innerSubject = .pollOption(bytes)` на сервер, который его молча отбрасывает (D-012): панель показывала фрагмент, а уходил обычный ответ. Теперь область перекладывается в текст в `ChatControllerImpl.transformEnqueueMessages`, через который проходят все отправки: первое сообщение с текстом (текст или подпись к медиа), где хватает места под маркер, получает его; все сообщения уходят с обычным reply subject. Стикеры, медиа без подписи, кубик и rich-сообщения становятся обычными ответами на фото, inline-результаты лишаются области явно (`withoutRegion`). Это записано в README как ограничение транспорта.
Там же: `breakChatInputText` режет текст ровно по 4096, а маркер добавлял символ сверх лимита; теперь `VisualQuoteTransport.chunks(of:)` оставляет в первом фрагменте место под маркер, а лимит редактора уменьшен на длину маркера. Редактирование больше не снимает превью ссылки, если пользователь его оставил. Проверки кодека покрывают преобразование исходящих сообщений и разбиение (4108 проверок).
Облачный черновик (проверка по находке ревью): в «Избранном» черновик с областью, набранный на одном симуляторе, на втором не появился, но и обычный ответ («Reply to Nika», без области) туда не пришёл: черновики этого чата между устройствами не синхронизируются, так что проверка ничего не говорит про транспорт. Проверка в обычном личном чате требует второго аккаунта и отложена вместе с ним; ограничение записано в README.
Прочие правки по ревью: выбор области недоступен для фото в чатах с запретом копирования (фрагмент в панели ответа не был защищён от скриншотов) и там, где нельзя писать (кнопка Reply показывалась, но ничего не делала); пассивная подсветка не накладывается на уже начатое выделение и сбрасывается при смене фото; детектор готовится заново при смене аккаунта и не держит первый контекст; генератор фрагмента декодирует фото один раз на каждое обновление сигнала, а не при каждой перекомпоновке; панель ответа рисует фрагмент тем же генератором, что и пузырь (`VisualQuoteCropView` удалён); убраны мёртвые варианты миниатюры, «хвосты» уголков, неиспользуемая маска детектора и `point(in:)`; кнопка Reply и приближение используют одну и ту же измеренную высоту панелей галереи.

## Демо-видео для конкурса (2026-10-15)

### D-036. Отладочный индикатор касаний для записи демо, только за аргументом запуска `--show-touches` (2026-10-15)
Демо-видео для конкурса записывается с симулятора в стиле роликов самого Telegram, где каждое касание показано полупрозрачным серым кружком. У iOS Simulator нет настройки «показывать касания», а средства записи экрана Mac кружки на симуляторе не рисуют. Поэтому кружок рисует сама сборка: `Telegram/Telegram-iOS/TouchIndicatorOverlay.swift` плюс две строки в `Application.swift`. Включается только если приложение запущено с аргументом `--show-touches` (`xcrun simctl launch <udid> ph.telegra.Telegraph --show-touches`), по аналогии со штатной проверкой `--ui-test` в `AppDelegate`; без аргумента ничего не создаётся и поведение приложения не меняется. К функции Visual Quote это не относится и в задание не входит, это инструмент для записи.
Устройство: касания читаются в `Application.sendEvent(_:)`, который видит события всех окон, включая окно системной клавиатуры (`NativeWindow.sendEvent` из Display их бы не увидел). Кружки живут в отдельном прозрачном окне (`isUserInteractionEnabled = false`, создаётся при первом касании, на hit-testing не влияет). Один `CALayer` на касание, ключ `ObjectIdentifier(touch)`. Вид: диаметр 26 pt, заливка чёрная 0,22, обводка 1,5 pt белая 0,65; появление масштабом 0,6 → 1 за 0,12 с, при движении кружок следует за пальцем без анимации, при отпускании гаснет за 0,2 с с ростом до 1,25. Корневой контроллер оверлейного окна повторяет стиль и скрытие статус-бара и ориентации корневого контроллера главного окна, потому что полноэкранное окно выше главного иначе перехватывает их (так же делает `TGOverlayControllerWindow`).
Клавиатура: UIKit обрезает `windowLevel` до 1e7 (запрошенные 1e9 в логе стали 10000000; собственные окна Telegram с уровнем 1e9, например в `TGModernConversationInputMicButton`, обрезаются так же), а окно системной клавиатуры `UIRemoteKeyboardWindow` стоит на 1e7 + 1, то есть выше любого окна приложения. В первой проверке касание клавиши доходило до `sendEvent`, но кружок оказывался под клавиатурой. Поэтому для окон с уровнем не ниже оверлея кружок добавляется в слой самого окна, которому пришло касание; проверено, что он виден поверх клавиши вместе со штатным увеличенным превью буквы.
Проверка на iPhone 17 Pro: запись `xcrun simctl io <udid> recordVideo` во время свайпа и тапов по списку чатов, полю поиска и клавише клавиатуры поиска, кадры `screenshots/demo/touch-overlay-list.png`, `touch-overlay-search.png` и `touch-overlay-keyboard.png`; запуск без аргумента кружков не показывает; статус-бар после появления оверлея не меняется.
Попутно: экранная клавиатура в симуляторах не показывалась, потому что к ним была подключена аппаратная клавиатура Mac (настройка Simulator.app «I/O → Keyboard → Connect Hardware Keyboard»). Для записи демо она отключена для обоих симуляторов (`defaults write com.apple.iphonesimulator ConnectHardwareKeyboard -bool false` плюс `DevicePreferences` по UDID; Simulator.app перезапущен без выключения устройств). Вернуть можно той же галочкой в меню Simulator.app.

### D-037. Рамка выбирает уголок или перемещение по точке касания, а не по месту, где начался пан (замечание Ники, 2026-10-16)
При записи демо быстрый жест от уголка маленькой рамки сдвигал рамку целиком вместо того, чтобы её растягивать. Причина: `VisualQuoteFrameNode` определял режим в `.began` пан-жеста по `recognizer.location`, а пан начинается только после того, как палец прошёл порог распознавания; у рамки 80×80 pt зона уголка — треть стороны, около 27 pt, и при быстром движении палец к этому моменту уже вне её. `translation` у пана отсчитывается от точки распознавания, поэтому восстановить из него точку касания нельзя. Теперь точка касания запоминается в `gestureRecognizer(_:shouldReceive:)` (первое касание жеста), и режим выбирается по ней; перемещение и размер рамки по-прежнему считаются по `translation`, поведение при медленном жесте не изменилось.
Проверка на iPhone 17 во время `simctl io recordVideo` (нагрузка, при которой баг воспроизводился): быстрый жест от левого верхнего уголка растягивает рамку, жест за середину её двигает, быстрый жест от правого нижнего уголка снова растягивает. Скриншоты в папке проекта: до — `screenshots/demo/frame-fast-drag-before.png`, после — `screenshots/demo/frame-fast-drag-after.png`.
